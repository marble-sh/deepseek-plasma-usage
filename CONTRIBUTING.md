# Contributing

Thanks for looking. This is a small widget with a deliberately small surface, so
most contributions are one of: a fix to a number the widget gets wrong, another
locale, or a layout problem. All three are welcome.

This file is English only, on purpose: a contributor guide that is itself machine
translated would be worse than none.

## What it is

A KDE Plasma 6 applet showing DeepSeek API balance and usage. The `README.md` covers
what it displays and where the data comes from; [`translate/README.md`](translate/README.md)
covers the catalogues. The non-obvious engineering constraints are:

- **No runtime dependencies** beyond Plasma and Qt. Network is QML
  `XMLHttpRequest`, parsing is plain JavaScript, KWallet is reached through the
  `kwallet-query` binary. Please do not add a runtime library.
- **The logic lives in `contents/ui/js/`** as plain scripts with no Qt APIs, so
  `node` can run them. If you are changing a number the widget shows, that is
  where it goes, with a test next to it.
- **`metadata.json` is the package manifest** and `contents/ui/*.qml` is the UI.
  `install.sh` stages and installs.

## Getting set up

You need a Plasma 6 session, `kpackagetool6`, `qmllint`, and gettext. Then:

```sh
git clone https://github.com/marble-sh/deepseek-plasma-usage
cd deepseek-plasma-usage
npm install          # prettier only; the widget itself has no dependencies
./install.sh         # install or upgrade for the current user
```

`install.sh --pack` writes the distributable `.plasmoid`, `--uninstall` removes it.
Credentials go in the widget's settings, or straight into KWallet as
`deepseek-api-key` and `deepseek-session-token` in the `Plasma` folder of
`kdewallet`.

You do **not** need live credentials to develop: `tests/mock-platform-server.mjs`
serves recorded payload shapes, and `tests/capture-screenshots.sh` drives the whole
mock set-up, including the widget install, for you.

## Before you push

Run the gauntlet. Every item must pass; they are the same things CI runs.

```sh
npm test                        # node --test tests/*.test.mjs
npm run format:check            # prettier
npm run lint:qml                # qmllint contents/ui/*.qml contents/config/config.qml
npm run check:po                # translate/build.sh --check
./install.sh                    # and then load the widget once
```

`npm run format` writes the formatting. `tests/capture-screenshots.sh` regenerates
the README images in every language, and `tests/capture-locales.sh` renders one
locale at a time so you can look for clipped or overflowing text — Hindi and
Russian run much longer than English.

## Formatting

Prettier owns the formatting of everything it can parse: JavaScript, JSON, YAML and
Markdown. It cannot parse QML, shell or gettext, so `.prettierignore` lists those —
and the files that are generated byte-for-byte elsewhere, such as
`translate/messages/` (the generator reads them), `translate/*.po`, `LINGUAS` and
the compiled `contents/locale/**/*.mo`. Do not hand-format a generated file; change
its source and regenerate.

Two options in `.prettierrc.json` are deliberate: `printWidth` is 120 because the
locale tables read much better at one entry per line, and `proseWrap` is
`preserve` so Prettier never rewraps the READMEs.

## Tests

```sh
npm test                        # everything
node --test tests/format.test.mjs   # one file
```

The tests load the QML-side scripts through `tests/load.mjs`, which runs them in a
`vm` context because they are plain scripts rather than ES modules. Locale data is
transcribed from CLDR through ICU, and `tests/format.test.mjs` asserts it a locale
at a time — if you add a locale, add its case there, and derive the expected
strings with Node rather than by eye:

```sh
node -e 'console.log(new Intl.NumberFormat("es-CL", {style:"currency", currency:"USD"}).format(1234567.89))'
```

## Translations

`translate/messages/<locale>.json` is the source of truth; the `.po` files and the
compiled `.mo` files are generated by `translate/generate.mjs` and
`translate/build.sh`. Adding a string means adding it to the tables, and the
generator will refuse to build if a translation is missing, has the wrong number of
plural variants, or drops a `%1` placeholder.

The shipped catalogues are machine translations and say so in their headers. Review
is welcome in any language, and Hindi, Russian and Simplified Chinese are the
priority. KDE's own translation teams are the route to reviewed translations; the
steps are in [`translate/README.md`](translate/README.md).

## Versioning

[Semantic Versioning](https://semver.org/spec/v2.0.0.html), with the policy spelled
out in [`CHANGELOG.md`](CHANGELOG.md). The version lives in `package.json` and in
`metadata.json` as `KPlugin.Version`; `tests/version.test.mjs` fails if they disagree
with the newest `CHANGELOG.md` heading.

Releasing is: move the `[Unreleased]` entries in `CHANGELOG.md` under a new dated
heading, bump the two version fields, commit, then tag and push the tag.

```sh
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
```

## Commits and pull requests

`main` is protected: changes arrive through a pull request, the CI checks have to
pass, and history is linear (squash or rebase, no merge commits). There is no
required reviewer, so a single maintainer can merge their own work.

Write commit messages that say _why_. The existing history is the model: each commit
explains the problem and the reasoning, not just the diff. Keep unrelated changes in
separate commits.
