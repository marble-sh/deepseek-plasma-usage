# Translations

The widget is translated with gettext/KI18n, the same way every Plasma applet
is. A plasmoid's own catalogue is looked up under the domain
`plasma_applet_<plugin id>`, which for this widget is
`plasma_applet_org.deepseek.plasma.usage`, in the package directory

```
contents/locale/<locale>/LC_MESSAGES/plasma_applet_org.deepseek.plasma.usage.mo
```

so no system-wide installation is involved.

## Layout

| Path                         | Role                                                                                                                |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `../Messages.sh`             | Entry point for KDE's translation automation. See "Getting this translated by KDE" below.                           |
| `template.pot`               | Extracted from the sources. Generated by `merge.sh`, committed.                                                     |
| `messages/<locale>.json`     | **Source of truth** for our translations. One table per locale, or a small override table on top of a base locale.  |
| `generate.mjs`               | Builds `<locale>.po` from `template.pot` + the tables.                                                              |
| `<locale>.po`                | Generated. Committed, because it is the format every translation tool and every KDE translator expects.             |
| `LINGUAS`                    | The list of locales we ship.                                                                                        |
| `crowdin.yml`, `.tx/config`  | Ready-made configs for handing the catalogue to an online platform. Unused unless you choose that route; see below. |
| `../contents/locale/**/*.mo` | Compiled catalogues, committed so `./install.sh` works without gettext.                                             |

## Workflow

```sh
./translate/merge.sh     # after changing i18n() calls: refresh template.pot
$EDITOR translate/messages/xx.json
./translate/build.sh     # regenerate *.po and compile *.mo
./translate/build.sh --check   # CI: fail if anything is out of date
```

`merge.sh` parses QML with the C++-like parser and the `js/` modules with the
JavaScript parser, because gettext needs a different parser per language. It
also emits the `#:` references as repo-relative paths.

`generate.mjs` refuses to write a catalogue that would fall back to English at
runtime or break a format string. These are hard errors:

- a msgid in the pot with no translation (and no base catalogue),
- a plural entry whose variant count disagrees with the locale's
  `Plural-Forms`,
- a translation that drops or invents a `%1`-style placeholder.

`msgfmt --check --check-format` is run again by `build.sh` as an independent
check.

## Table format

Keys are **gettext keys**, the same ones gettext uses internally:

```
[msgctxt + U+0004] + msgid [+ U+0000 + msgid_plural]
```

so `"token usage table row\u0004Cost"` is the entry for `i18nc("token usage
table row", "Cost")`, and `"Last %1 day\u0000Last %1 days"` is the plural entry.
Values are strings, or arrays with one element per `Plural-Forms` variant
(1 for zh_CN/id_ID, 2 for hi_IN/fr_FR/es_*, 3 for ru_RU/ru_BY).

A table with a `base` key starts from another locale and applies its own
`overrides`. Two aliases exist because Qt looks up `<lang>_<REGION>` and then
bare `<lang>`, so the bare entries widen coverage at no cost:

- `es_CL`, `es_AR`, `es_MX`, `es_CU` are aliases of `es_419`. This is
  deliberate: **none of the current strings differ between them.** If one ever
  does, give that locale its own `base` + `overrides` and it stops being a copy.
- `es_ES` inherits `es_419` and overrides the handful of strings where Spain
  differs (`ajustes` vs `configuración`, `importes` vs `montos`, …).
- `ru_BY`, `ru`, `fr`, `id`, `hi` are aliases of their regional catalogue.
- `en_IN` is an identity catalogue (each msgstr equals its msgid).

## Status: unreviewed machine translation

> [!WARNING]
> **Every catalogue in this directory is machine-generated and has never been
> reviewed by a native speaker.** Each `.po` says so in its header
> (`Last-Translator: Unreviewed machine translation`) and the `Language-Team`
> field is still gettext's "no team has claimed this file" placeholder. Treat
> them as a solid starting point, not as finished translation.
>
> **Priority for review: Hindi (`hi_IN`), Russian (`ru_RU`/`ru_BY`) and
> Simplified Chinese (`zh_CN`).** Those three are the languages this widget is
> most likely to be used in, and they are the ones where an unreviewed
> translation is least acceptable. Everything else is a bonus.

Harmless, expected `msgfmt` warning:

```
warning: header field 'Language-Team' still has the initial default value
```

That placeholder is accurate, and it disappears once a real translation team
adopts a catalogue.

## Getting this translated by KDE

**This is the chosen route** (decision D13 in `docs/decisions-log.md`): KDE's
per-language translation teams, rather than a machine translation or a
commercial platform. It is the only route that produces _reviewed_ translations
by people who actually speak the languages, which is the whole point.

### It has a precondition

KDE's translation automation runs over KDE's own repositories and merges into
KDE's translation repositories. So this only starts working once the widget
lives in a KDE repository (for example on `invent.kde.org`) **and** has been
picked up by the translation team — being on Invent alone is not enough. Until
then, nothing here blocks you: the catalogues in this directory keep shipping.

### What is already in place

- `Messages.sh` in the repository root is the entry point KDE's tooling runs.
  It is written to the convention used by KDE's own packages and was smoke-
  tested with a simulated `$XGETTEXT`/`$podir` environment: it extracts the same
  70 msgids as `translate/merge.sh`, and names the pot
  `plasma_applet_org.deepseek.plasma.usage.pot` — the basename **is** the message
  domain the applet loads, so it must not be renamed.
- The strings are already marked up correctly (`i18n()`, `i18nc()` with a
  context where the string is ambiguous, and plural forms), which is what makes
  a catalogue translatable in the first place.
- `translate/template.pot` and the `.po` files are in gettext's standard format,
  so they can be offered as a **pre-translation seed** rather than thrown away.

### What to do, in order

1. Get the widget into a KDE repository, or get it adopted into an existing one
   (it is a Plasma applet, so `plasma/` is the natural home).
2. Check `Messages.sh` still produces the same msgid set there:
   `XGETTEXT=xgettext podir=/tmp/potest bash Messages.sh`.
3. Ask the translation team to include it. The KDE wiki lists the contact
   points as the **`#kde-i18n`** channel on Matrix/IRC and the
   **`kde-i18n-doc`** mailing list; translation-infrastructure issues are
   tracked on Invent. Say explicitly that the existing catalogues are unreviewed
   machine translations, so reviewers know what they are inheriting.
4. Once KDE owns the catalogues, `.po` ownership moves to KDE's translation
   repositories. At that point delete `messages/`, drop the `generate.mjs` step,
   and keep `merge.sh` and `build.sh` for checking and compiling locally.

### What I could not verify

The KDE wiki states that KDE stores translations in **SVN** and that translators
use **Lokalize**; it does not document WebLate. I previously described WebLate
as the KDE tool — that was wrong, or at least unsupported by the pages I could
reach, and it is corrected here. There is no Scripty documentation page on the
wiki either (the `Infrastructure/Scripty` page is empty), so the exact current
procedure for getting a project picked up by the translation automation is worth
confirming on `#kde-i18n` before relying on it.

## Fallback: online translation platforms

Only relevant if the KDE route above turns out to be unavailable — for example
if the widget never lands in a KDE repository. Both configs are checked in and
**neither has ever been run**; creating the project, applying for the
open-source plan and inviting translators are human actions.

- **Transifex** states on its open-source page that it is free forever for
  projects whose source is public, OSI-licensed and has _no funding, revenue or
  commercialisation model_. This project is GPL-2.0-or-later and unfunded, so it
  would qualify.
- **Crowdin** has an open-source programme too, but its open-source page
  returned 404 for me, so treat `crowdin.yml` as a starting point rather than a
  tested setup. Note it has no "Spanish, Cuba" locale, so `es_CU` would have to
  be served by `es-419`.

> **Pick one source of truth.** Today `messages/*.json` is authoritative and the
> `.po` files are generated. The moment a reviewer or a platform owns the
> catalogue, the `.po` files become authoritative instead: delete `messages/`,
> stop running `generate.mjs`, and keep `merge.sh` (to refresh
> `template.pot`) and `build.sh` (to compile). Nothing else depends on the
> tables, and `build.sh --check` will tell you if the `.po` files and the
> committed `.mo` files drift apart.
